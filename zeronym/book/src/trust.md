# Trust and honest limits

Zeronym's migration-privacy guarantee rests on a chain of mechanisms, documented here end to end:

- the **Nym 5-hop mixnet** that unlinks a shim from the hub, so the hub cannot tell which operator or region a migration came from;
- **AWS Nitro attestation** over a **reproducible StageX build**, making the exact software in each enclave checkable rather than asserted;
- **STEVE**, Caution's one-way enclave handshake, by which the shim verifies the hub before handing over a migration;
- the **keymaker / locksmith M-of-N quorum**, a governance mechanism (separate from STEVE) that persists keys across cold boots and upgrades and hands every hub the same shared key;
- the **Auditor Role**, which lets any independent third party confirm a public endpoint is really running the reviewed software, without trusting the operator.

The same attestation makes the **attested edge** protections real: that the operator's front-end is exactly the reviewed shim code, and its promise not to log requester IPs is verifiable, not merely trusted. See [the introduction](./introduction.md) for what that edge protects and [review](./review.md) for claims still awaiting sign-off. [The architecture](./architecture.md) owns the two trust-plane diagrams and the three nested encryption layers; [the roadmap](./roadmap.md) covers PIR (V3) as the step that removes the hardware trust root.

**What is trusted, and what is not.** The near-term system trusts the AWS Nitro platform and its hardware root of trust, and the people who review the open source and reproduce its build hash. It does **not** trust the operator running the shim, the host running the hub (Caution at launch), the Nym client or mixnet, or the full nodes the hub broadcasts through. Those parties see only ciphertext on the migration path; the attestation chain lets a wallet (or an auditor acting for it) check that this is so.

## The Nym transport (shim to hub)

Nym is used for exactly one hop: **shim to hub**. Wallets do not speak Nym; a naive wallet reaches the shim over ordinary TLS, and all query and non-migration traffic flows from the shim to the operator's backing lwd over the local network. Only an isolated migration is routed over Nym, from the shim's side to the hub's. This is the same boundary STEVE observes: both live only on the shim-to-hub channel, never on wallet-to-shim.

**The mixnet.** Nym is a 5-hop mixnet. The encrypted migration is wrapped in a **Sphinx** packet and relayed through independent mix nodes, each peeling one layer and forwarding, so no node sees both source and destination. **Cover traffic** (steady dummy packets indistinguishable from real ones) makes the flow unlinkable in time and volume: the hub cannot tell which region or operator a migration came from, and a network observer cannot pick the real migration out of the cover. This breaks the "IP X was active at time T" to "on-chain migration at time T" correlation for naive wallets.

**The proxy pair.** Per `deploy/caution-zaino/NYM.md`, the transport uses the nym-sdk `TcpProxy` binaries: **`nym-proxy-client`** on the shim side and **`nym-proxy-server`** fronting the hub. The shim opens a Nym tunnel to the hub's Nym address; the encrypted migration rides inside it, appearing to the shim as a local TCP endpoint. Nym mainnet uses ticketbook ecash credentials, so the Nym client needs Nyx-RPC egress (`rpc.nymtech.net:443`) to obtain them, a real operational dependency, not just an IP route.

**The Nym client is untrusted.** Deliberate and load-bearing: the migration is already encrypted to the hub's enclave key before it enters the tunnel (the inner layer in [the architecture](./architecture.md)), so the Nym client, mix nodes, and parent host see only ciphertext. `nym-proxy-client` can run as an ordinary sidecar (in-enclave on managed Caution only because we do not control the parent there, parent-side on BYOC), and `nym-proxy-server` runs parent-side at the hub. A compromised Nym path yields only ciphertext and mixnet-obscured timing. Whether `nym-proxy-server` may run parent-side on managed Caution or must run in-enclave is open for Caution (see [review](./review.md)).

**Validated, not assumed.** In the V2 rehearsal (2026-07-30), nym-proxy built from `nymtech/nym` carried real `CompactTxStreamer` gRPC over the live Nym **mainnet** mixnet against a live testnet node, end to end. Throughput is roughly 10x slower than clearnet (unary calls ~9 to 10 seconds, `GetBlockRange` ~19 blocks per second, latency-bound, first one or two calls warming up before steady state). Fine for migrations, which are not time-sensitive, and it de-risks the shim-to-hub tunnel and the enclave attestation riding on top.

## TEE attestation (AWS Nitro)

Both binaries, the shim and the hub, run inside **AWS Nitro enclaves**. The enclave makes operator-blindness real and checkable: a non-enclave shim would let the operator read migration contents, and a hacked adjacent node could peer at outbound transactions. Nitro provides hardware memory isolation (parent instance and host cannot inspect enclave memory) and a hardware root of trust that signs a statement about the software inside. The design additionally assumes the enclave resists **state rollback** (rewind/replay) and **memory-access-pattern observation**; hardening for both is an open item (see [review](./review.md)). This is a **detection-based** defense: it aims to make attacks that fall short of a fully-compromised TEE (or a certificate outside CT) detectable after the fact rather than to prevent them outright (see [the problem](./problem.md)).

**Reproducible build, root hash.** Both binaries are **static-musl** and built reproducibly with **StageX** (`SOURCE_DATE_EPOCH=1`), following the `deploy/caution-zaino/combined/` Containerfile pattern. A reproducible build means anyone with the source produces a bit-identical image and the same measurement hash. That hash is the anchor of the whole chain, which runs: **rebuild from source, get the same hash, match it against the hash bound into the attestation.** Break the first link and the rest carries no weight. An attestation on its own proves only that *some* binary is running inside a genuine enclave; it says nothing about whether that binary corresponds to the source anyone reviewed. Without reproducibility the detection design collapses into trusting whoever compiled the binary, which is exactly the party it refuses to trust. Reproducibility is a prerequisite for the trust model, not build hygiene.

**Status: the source-to-hash link is built and reproduced locally, with independent-hardware confirmation of the current hash outstanding.** The shim has a StageX recipe at `zeronym/shim/deploy/`, a sibling of the `deploy/caution-zaino/combined/` pattern. The last measured binary hash is `c6b7738f6ac2f6f2e6cb58c5b63d4c40b7e4903d057c5a44adcf7b0e01fe1a6a` (the machine-readable copy is `deploy/EXPECTED_SHA256`), and five cold builds, from three separately assembled contexts on one host (arm64 macOS, amd64 under emulation), all landed on it. That is determinism on one machine, not yet cross-machine agreement, and it is the hash of the source as it stood at that measurement: a later review pass touched compiled code again, so the first build after the commit **re-baselines** that value rather than confirming it. The two builds on record from a native x86_64 CI runner attest the **recipe on the old source**: they landed on `a9c19f2c3c878da0e2048ff05c075e017a960b3c81c43b631be53f424462ce05`, which is the pre-2026-08-01 classifier and is superseded. That pair is still worth something, because it differs from the local builds in machine *and* in how the compiler itself was executed, which rules out codegen that varies with runtime CPU feature detection in a way two native builds would not have; but it says that about the recipe, not about today's binary. Independent reproduction of `c6b7738f…` is pending for a mundane reason: the predicate change it compiles is deliberately uncommitted, so CI cannot see the source. The closing step is to land the commit and re-run the reproduce workflow. `zeronym/shim/deploy/README.md` carries the same caveat in the same terms. Building it settled the three requirements the PoC had surfaced:

- **A context spanning the vendored subtrees** (solved). The crate path-depends on `zebra/zebra-chain` and `zaino/packages/zaino-proto`, so a per-crate context cannot work. An assemble script composes a repo-shaped context with `git archive HEAD`, which both resolves the path deps unchanged and structurally prevents the build from dirtying a vendored subtree.
- **`zaino-proto` pinned to `default-features = false`** (solved, and double-locked). Its `heavy` default lets its `build.rs` find `protoc` and regenerate its committed protos *inside the vendored subtree*, and pulls a second `zebra-chain` from crates.io. A build that rewrites its own inputs is not reproducible. Beyond the feature pin, the image simply ships no `protoc`, so the regeneration path cannot execute whatever happens to features. The tripwire stays cheap: `git status --porcelain zaino/ zebra/` must be empty after a build.
- **A committed lockfile** (done), pinning a parser that is not yet the node's (still open). `Cargo.lock` makes the classifier's parse deterministic rather than whatever resolves on build day. It is not *identical* to the node's: the shim is its own workspace, so it does not inherit zebra's `[patch.crates-io] orchard = { path = "../orchard" }`, and resolves `orchard 0.15.4` from crates.io while zebra's binaries build the vendored `0.15.0`. The lockfile pins that gap rather than closing it; closing it means the shim carrying its own `[patch.crates-io]` or joining a repo-root workspace.

What remains is the **second** link, and it is the larger one: nothing here has run inside a Nitro enclave. No PCR has been computed from this image, no EIF assembled, no attestation document produced. So the hash exists and the recipe for deriving it is published (with the caveat above: reproducing today's hash needs the commit to land first), but the hash-to-attestation binding that motivates the whole exercise is still designed rather than demonstrated. The hub has no reproducible build yet either.

**In-enclave keygen and NSM binding.** Each enclave generates its key **at boot, inside the enclave** (the private key never leaves) and binds the **public key** into the attestation produced by the **Nitro Security Module (NSM)**. The attestation is a COSE_Sign1 document, signed up to the AWS Nitro root, carrying the enclave's **PCRs** (platform configuration registers measuring the loaded software, i.e. the StageX root hash) alongside the bound public key. Verifying it proves both: the software is exactly the reviewed build, and the public key was born inside that software rather than handed in by the host.

The shim binds its **TLS public key** (see [the shim](./components.md) for the ACME cert model), so an auditor can check the certificate a wallet sees is keyed to an enclave-born key. The hub binds its **hub public key**, the key shims encrypt migrations to. Attestation binding is achievable three ways on Caution's platform (confirmed at V2): via the STEVE handshake, via the pubkey injected through `metadata.json` into `user_data` (which implies a persisted key), or via a new runtime `arbitrary_data` field Caution would add. The specific mechanism, and how `/attestation` is delivered for a zero-ingress service, are open for Caution (see [review](./review.md)). The two unknowns Zooko flagged, exactly what can be attested and how memory peeking is prevented, are substantially answered here: Nitro's memory isolation blocks host reads, and Caution's binding ties the enclave-born key to the measured software.

## STEVE

**STEVE** ("Secure Transport Encryption Via Enclave") is a Distrust protocol integrated into Caution, documented at `distrust.co/blog/steve.html` with source at `git.distrust.co/public/steve`. It is a **second encryption layer that terminates inside the enclave**: when an outer transport terminates outside the enclave, STEVE gives a channel whose plaintext exists only within the TCB.

**Scope.** Used **only on the shim-to-hub channel**, carrying the `SubmitMigration` request/response exchange. **Not** used on wallet-to-shim (naive wallets speak plain TLS, which terminates inside the shim enclave on its own). In [the architecture](./architecture.md)'s three-layer stack, STEVE is the **middle** layer: it wraps the payload already encrypted to the hub key (inner) and is itself carried inside the Nym Sphinx packet (outer); its AES-256-GCM plaintext is exposed only inside the hub enclave.

**One-way handshake: the client (shim) verifies the enclave (hub)**, not the reverse:

1. The client checks the hub's **attestation and PCRs against the AWS Nitro root**.
2. It extracts the enclave's **Ed25519** identity key from the attested material.
3. It sends an ephemeral **X25519** public key.
4. It receives the enclave's ephemeral key plus an **Ed25519 signature** over that ephemeral key.
5. It **verifies the signature** against the attested Ed25519 identity key.
6. Both sides derive a session key by **X25519 ECDH followed by HKDF-SHA256**.
7. Payloads are **CBOR encoded and encrypted with AES-256-GCM**.

STEVE runs as a **reverse proxy on `:8080`**: on the hub side the STEVE server decrypts inbound migrations inside the enclave; on the shim side the STEVE client performs the verification before any migration is sent. The **Rust SDK is still in development** (the JS SDK ships today), which is why implementing the handshake directly from standard primitives is a fallback (see [review](./review.md)). Because the handshake is the shim verifying the hub's attestation and extracting its bound key, **the STEVE handshake is itself an act of auditing**, the same enclave-verification the Auditor Role performs, just automatic and per session.

**Two open STEVE items** go to Caution: the exact **wire form over Nym** (does a STEVE session carry gRPC / h2, or a raw framed byte stream we frame ourselves), and **mutual vs one-way** (one-way suffices for privacy; making the hub also verify the shim's attestation would additionally gate abuse). Both in [review](./review.md).

**STEVE is not the quorum.** The keymaker / locksmith quorum below is a **separate** Caution mechanism. STEVE is a per-session handshake that verifies an enclave and derives a transport key; the quorum is a governance and persistence mechanism for long-lived keys. They solve different problems.

## The keymaker quorum (separate from STEVE)

Enclaves are diskless and ephemeral: a key generated in-enclave at boot is lost on every restart, and a software upgrade changes the measurement so a KMS-seal-to-PCR scheme would refuse to unseal the old key. Zeronym needs long-lived keys anyway (a stable TLS key and address for the shim, one hub key every hub instance shares), so it uses a **keymaker / locksmith M-of-N quorum**.

**What it is.** An M-of-N key-custody mechanism spread across **3 to 4 organizations**: the proposed consortium of Caution, Nym, Shielded Labs, and the Zcash Foundation. It reconstitutes a key inside a fresh, attested enclave across both **cold boots and software upgrades** (strictly better than sealing to PCRs, which breaks on upgrade). Private key material is only ever reassembled inside an attested enclave; no single org holds it.

**What it persists.** For **the shim**: the TLS keypair, giving the shim's public URL a **stable key and address** across boots and upgrades, so the endpoint does not churn its identity and the ACME cert can renew against a stable key. For **the hub**: **a single shared hub key across all instances**. A shim encrypts a migration to "the hub key," and **any** attested hub instance can decrypt, dedup, and publish it. Per-hub keys would force re-encryption on failover and strand a migration whose hub died mid-flight. With one shared key provisioned to every attested hub by the quorum, running two or more hubs with shim failover (see [the hub](./components.md)) costs nothing in key management; a rare double-publish is a harmless on-chain duplicate, deduped by txid.

**Governance trajectory.** The quorum is also the long-term **trust-distribution** goal: the consortium collectively attests to key state and software integrity, so no single party (not even Caution) unilaterally controls the hub key. For launch this is staged: a single trusted entity (Caution) stands up the hub, with the multi-org quorum to follow. The consortium's several organizations are the natural operators of the standby hubs, where decentralization of the hub itself begins.

## The Auditor Role

The drop-in model creates a verification problem: a wallet connects to a familiar public URL (say `zec.rocks:443`) and needs to know it is really fronted by the reviewed shim enclave, not an operator who quietly kept the plaintext. The **Auditor Role** answers this **without trusting the operator**, and passes the assurance on: in practice a wallet developer acts as the trust proxy, audits once, and every user of that wallet inherits the result.

Steps for a public lwd endpoint:

1. **Fetch the endpoint's TLS public key and certificate** directly over HTTPS.
2. **Load its attestation.** POST a nonce to `/attestation` and receive a COSE_Sign1 document, proving the private key was **generated inside the enclave** and carrying the **root hash of the software** there.
3. **Verify the PCRs against the AWS Nitro root.** Confirm the attestation chains to the genuine Nitro hardware root of trust and the measured software matches expectations.
4. **Reproduce the build.** Run the reproducible StageX build from source, obtain the hash, and confirm it equals the attested root hash, tying "the reviewed source" to "the software actually running." This is the step nothing in Zeronym has passed yet (above), and the step the other three are worthless without.
5. **Check Certificate Transparency.** Confirm **no other currently-valid certificate exists** for the domain. Otherwise an operator could present the attested, enclave-born cert to auditors while serving a different, non-enclave shadow cert to real users and MITM them. All Let's Encrypt certificates are CT-logged, and the shim obtains its cert via in-enclave ACME precisely so this check is meaningful (see [the shim](./components.md)). CT closes the cert-substitution gap the public-URL drop-in would otherwise leave open.

Concrete probes against a running enclave (the node IP here is an ephemeral testnet enclave):

```
curl -sk -X POST -H 'Content-Type: application/json' \
  -d '{"nonce":"00112233445566778899aabbccddeeff"}' https://<node-ip>/attestation
grpcurl -plaintext \
  -import-path <zaino>/packages/zaino-proto/lightwallet-protocol/walletrpc \
  -proto service.proto <node-ip>:8137 \
  cash.z.wallet.sdk.rpc.CompactTxStreamer/GetLightdInfo
```

The hub is audited the same way, and **the shim's STEVE handshake is the shim performing exactly this audit of the hub** on every session before it trusts a hub with a migration. Independent auditors run the same steps out of band; reproducibility is what lets the consortium and third parties confirm that the running hub is the reviewed hub.

## What this trusts, and what it does not

| Party | Trusted? | Why |
|---|---|---|
| AWS Nitro manufacturer + platform | Yes (the trust root) | Hardware root of trust signs the attestation; memory isolation blocks host peeking |
| Reviewers who reproduce the build hash | Yes | The StageX hash is only meaningful if someone recomputes it, and for Zeronym's own binaries no one has yet (above) |
| Operator running the shim | No | Sees only TLS that terminates in the enclave; Orchard exits never reach its backing lwd (see [the shim](./components.md)) |
| Hub host (Caution at launch) | No | Sees only STEVE ciphertext; cleartext exists only inside the attested hub enclave |
| Nym client + mixnet | No | Payload is already encrypted to the hub key before it enters the tunnel |
| Full nodes the hub broadcasts through | No | Receive only the final, wallet-signed, batched transactions, unlinked from any source IP |

The honest consequence: the resulting privacy trusts **AWS and the hardware, not mathematics**. That is a deliberate near-term choice. The hardware-independent alternative that removes this trust root is PIR, complementary to the TEE rather than a replacement (distinct failure modes). That is the V3 story in [the roadmap](./roadmap.md), and the limit is developed below.

## Honest limits

The near-term system is a deliberate first step, buying the bulk of the practical migration privacy (IP unlinkability for the broadcast) at a fraction of the full indexer-in-a-TEE cost. None of the limits below is a bug to be quietly patched later: each is a structural consequence of the design, and stating it plainly is required for launch and any blog post. The framing the team accepted (README section 5, item 4): IP protection is the bulk of the necessary privacy here, and public-chain visibility only shows that *an entity* holds a balance, not *who*. The counter-caution, also on record: privacy is an arms race, and gains past the first roughly 70 to 80 percent cost exponentially more. So this is a Pareto first step. The robust, volume-independent win is IP unlinking via Nym; the properties below are weaker, conditional, or out of scope. One scope reminder: the system protects the migration *broadcast*, not queries. Which addresses a wallet looks up still passes through the shim to the operator's backing lwd exactly as today (query privacy is the deferred vision, see [the roadmap](./roadmap.md)).

**The operator learns that a client migrated, not the amount.** The shim forwards all traffic to the backing lwd untouched, with exactly one exception: an Orchard exit (a *migration* in the code's terms, see [the shim](./components.md)) is the one request it does *not* forward, encrypting it to the hub key and routing over Nym instead. That asymmetry is observable, so an operator watching its own host's traffic can infer that a given source IP submitted a migration, and roughly when, because that one request behaves differently from everything else. It does **not** learn *which* on-chain transaction or *what amount*: the hub batches the migration with every other operator's clients and publishes them simultaneously, unordered. The residual is "IP X migrated something, around time T," not "IP X migrated amount Y into transaction Z." (Contrast today's clearnet path, where the operator sees source IP, timing, and can retrospectively link IP to the cleartext on-chain transaction to the balance.) This inherent residual drives a firm decision: **shim-side batching and shim-to-hub cover traffic are rejected.** Both were proposed to hide the fact of a migration from the operator (batch a second time inside the shim, or send dummy shim-to-hub traffic), but a migration is by construction the one request the shim withholds from the backing lwd, so traffic analysis at the operator recovers the fact regardless of padding or delay. The genuine defense is hub batching (hides the on-chain transaction and amount), not a doomed attempt to hide the fact. A future Nym-aware wallet speaking to the hub directly sidesteps the operator and this residual disappears for it; near-term wallets are naive TLS clients, so the residual stands.

**The anonymity set is the cross-operator batch, and it can be one.** What hides which on-chain migration belongs to a client is the batch: the set of migrations from *all* shims that the hub publishes together in one flush. An operator never sees other operators' clients, so mixing happens at the hub across the whole network. Batch size is the key privacy metric for the timing property, and the [hub](./components.md) logs the achieved batch size honestly rather than assuming it. The weakness: this anonymity is only as strong as migration density in a single flush window. A batch of one is not anonymous; an on-chain observer sees a single migration appear. During the acute Orchard to Ironwood window density is natural (the whole reason to batch that mass, non-time-sensitive event); outside it, or in a globally thin period, batches can be small or singular. Two honest points: the flush cadence is capped by transaction expiry (flush before the tightest queued expiry, in practice well under 20 blocks), so the window **cannot** be widened to accumulate more migrations, there is no latency-for-batch-size lever past that ceiling; and the only backstop for a thin window is hub-generated decoy migrations, which cost real on-chain value, so they are a last resort, not the primary mechanism. Report the achieved batch size; do not present the batch-timing property as if it held at any volume.

**Broadcast is delayed, and the shim accepts before the chain does.** The shim returns an accepted response to the wallet immediately, synthesizing success as soon as it queues the migration for the hub. But the transaction is not in any mempool until the hub flushes, up to roughly 25 minutes later (blocks target about 75 seconds, flush on a strict block cadence under 20 blocks). Until then a wallet polling "in the mempool or confirmed?" is asking the backing lwd, which passes the query through, has no knowledge of the queued migration, and answers "not found" for minutes. Migrations are not time-sensitive, so the delay is acceptable by design. The batched class is wider than migrations, though: every Orchard exit is delayed, including a deshield straight to transparent (see [the shim](./components.md)). That is a real widening of what waits, and it costs little for a structural reason: Orchard is closed to new value, so ordinary commerce lives in Ironwood and passes through instantly, and what remains in Orchard is legacy balance whose movement is not urgent. The real cost is UX (the pending gap can confuse a UI or trigger a resend). The system tolerates resends (the hub dedups by txid, the shim is idempotent per txid within a window), but the pending-state experience must be defined: either wallets accept a bounded pending window for migrations, or the shim answers pending-status for txids it has queued. A sharp edge: because the shim returns success before the hub validates and broadcasts, an invalid migration receives a false success and fails silently at flush. The mitigation is stateless pre-validation (parseable, not already expired) at the shim and again at the hub; full consensus validity is only known at broadcast, and surfacing a late hub-side failure to the client is out of near-term scope.

**Retain-until-confirmed is a hard requirement, because the hub is diskless.** The hub runs in an attested enclave with no disk; its pending queue and awaiting-confirmation set live in RAM, and a crash loses them. This forces a non-negotiable obligation onto the shim: **the shim must retain each migration until it observes the transaction confirmed on-chain, not merely until it gets an Ack from a hub, and re-submit if a hub crash lost it.** Without this, a hub crash between accept and publish would silently drop a migration the wallet already believes was accepted. A diskless hub keeps the enclave TCB small and its restarts cheap, at the price of making the shim the durable party. The shim uses each migration's expiry slack (roughly 25 minutes to 2 hours depending on wallet family) as its retry budget: it holds, retries, and fails over across hubs, and only gives up into the last-resort direct broadcast (below) if expiry approaches. The shim's own restart durability is weaker (it too is diskless, so an in-flight migration in RAM is lost on shim restart); the mitigation there is a short Ack-pending window plus the wallet's resend and hub dedup. Diskless-hub plus retain-until-confirmed-shim is a coupled pair; neither half is optional. The queue, dedup, and confirmation-tracking engineering lives with [the hub](./components.md).

**The trust root is AWS and the hardware, not math.** The operator-blindness and hub-blindness guarantees are real and verifiable, but they rest on a hardware root of trust, not cryptography that stands alone. A wallet (or a developer acting as trust proxy) checks the shim's and hub's attestations against the AWS Nitro root, confirms the reproducible-build hash matches, and thereby knows the attested software is running and that keys were born inside the enclaves. That chain is only as strong as the AWS Nitro platform and the physical boundary of the hardware. If you do not trust AWS and the hardware, the near-term system gives no purely mathematical fallback. This is the specific gap the deferred PIR layer (V3) closes: PIR makes query privacy hold *via math*, hardware-independent, and closes the access-pattern and IO-pattern leaks a Nitro enclave structurally has when its state is parent-mediated at mainnet scale. TEE and PIR are complementary, not equivalent, with distinct failure modes (a TEE fails on hardware-manufacturer or physical-boundary compromise; PIR fails on cryptographic or software flaws), so the endgame uses both, defense in depth, with PIR as the trust-root-removal step (see [the roadmap](./roadmap.md)).

**Hub resilience, and the concentration of trust.** The hub must hold every migration in order to publish it, which makes a single hub both a liveness risk (an outage would stall migrations) and a concentration of trust (all cross-operator batching converges on it, run by Caution at launch). The design bounds this but does not eliminate the central point. The resilience measures (detailed as engineering in [the hub](./components.md)):

- **At least two attested hubs with shim failover.** A shim prefers a primary hub (so batches converge there and stay dense) and fails over to a hot standby only when the primary is unreachable. An outage on one hub does not stop migrations.
- **A single shared hub key across all instances**, provisioned to each attested hub by the keymaker quorum. A shim encrypts to "the hub key," and any instance can decrypt, dedup, and publish. Per-hub keys would force re-encryption on failover and could strand a migration whose hub died mid-flight.
- **Dedup by txid at every hub.** If failover causes a migration to reach two hubs, both may publish; the second on-chain submission is a harmless already-known duplicate. No cross-hub state sync is needed near-term.
- **Shim hold-and-retry using expiry slack.** The shim rides out transient blips with each migration's expiry margin before escalating.
- **Last-resort direct broadcast over Nym.** If every hub is unreachable and a queued migration nears expiry, the shim broadcasts it directly over Nym rather than let it expire. The IP is still hidden (Nym), but the batching is lost for that one transaction, so its timing anonymity degrades even as it still confirms.

The governing principle: an outage degrades privacy at the margin (a lost batch, a direct broadcast), never liveness (a migration never simply expires in a buffer). Because the hubs are attested enclaves, no hub operator sees cleartext, and the multi-org consortium governs the keys long-term; at launch a single trusted entity stands up the hub, with the consortium to follow. That launch concentration is part of the honest accounting: the trust distribution is a goal, not a shipped property on day one.

**How to report these limits.** Lead with the robust, volume-independent claim (IP unlinking for the migration broadcast, via Nym and the TEE) and qualify the conditional ones: the batch-timing anonymity depends on migration density and can be size one; the operator can infer the fact of a migration though not its amount; the broadcast is delayed; the trust root is AWS and the hardware, not math. Report the achieved batch size rather than an assumed one. Underclaiming here is cheap; overclaiming is the failure mode this chapter exists to prevent.

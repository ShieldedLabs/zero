# Honest limits

The near-term Zeronym system is a deliberate first step, not the whole product. It buys the bulk of the practical privacy at stake in the migration (IP unlinkability for the migration broadcast) at a fraction of the cost of the full indexer-in-a-TEE design. It does not buy everything, and the value of the system depends on saying exactly where it stops. This chapter is that accounting. None of these limits is a bug to be quietly patched later: each is a structural consequence of the design choices, and stating them plainly is a requirement for the launch and for any blog post that describes the system.

The framing the team accepted (README section 5, item 4): IP protection is the bulk of the necessary privacy here, and public-chain visibility only shows that *an entity* holds a balance, not *who*. The counter-caution, also on record: privacy is an arms race, and gains past the first roughly 70 to 80 percent cost exponentially more. So this is a Pareto first step, labeled as such. The robust, volume-independent win is IP unlinking via Nym; the other properties below are weaker, conditional, or explicitly out of scope.

One scope reminder that colors everything here: the system protects the migration *broadcast*, not queries. Which addresses a wallet looks up still passes through the shim to the operator's backing lwd exactly as today. Query privacy is the deferred vision, not a near-term property (see the [roadmap](./roadmap.md)).

## The operator learns that a client migrated, not the amount

The shim is a drop-in in front of an operator's existing backend. It forwards all traffic to that backing lwd untouched, with exactly one exception: a migration is the one request the shim does *not* forward to the backing lwd. It encrypts that request to the hub key and routes it over Nym instead. That asymmetry is observable. An operator running the shim, watching its own host's traffic, can infer that a given source IP submitted a migration, and roughly when, because that one request behaves differently from everything else the client sends.

What the operator does **not** learn is *which* on-chain transaction, or *what amount*, that migration is. The hub batches the migration together with migrations from every other operator's clients and publishes them simultaneously, unordered. So the residual is "IP X migrated something, around time T," not "IP X migrated amount Y into transaction Z." The threat-model row "linkable to source IP" is therefore No for the amount and the on-chain transaction, while the bare fact of a migration is inferable at the operator. Contrast today's clearnet path, where the operator sees the source IP, the timing, and can retrospectively link IP to the cleartext on-chain transaction to the balance.

This residual is inherent to the drop-in model, and it drives a firm design decision: **shim-side batching and shim-to-hub cover traffic are rejected.** Both were proposed as ways to hide the fact of a migration from the operator (batch migrations a second time inside the shim, or send dummy traffic from the shim to the hub so the migration does not stand out). Neither works, because a migration is by construction the one request the shim withholds from the backing lwd, so traffic analysis at the operator recovers the fact regardless of how the shim pads or delays. Spending effort there buys nothing real. The genuine defense is hub batching, which hides the on-chain transaction and amount, not a doomed attempt to hide the fact of a migration from the host the client already connected to. If a future wallet speaks to the hub directly (a Nym-aware wallet encrypting end to end), that wallet sidesteps the operator entirely and this residual disappears for it; near-term wallets are naive TLS clients, so the residual stands.

## The anonymity set is the cross-operator batch, and it can be one

What hides which on-chain migration belongs to a given client is the batch: the set of migrations from *all* shims that the hub publishes together in one flush. An operator never sees other operators' clients, so mixing happens at the hub across the whole network, not at any single operator. Batch size is therefore the key privacy metric for the timing property, and the [hub](./hub.md) logs the achieved batch size honestly rather than assuming it.

The weakness is that this anonymity is only as strong as migration density in a single flush window. A batch of one is not anonymous: if only one migration lands in a flush, co-publishing hides nothing, and an on-chain observer sees a single migration appear. During the acute Orchard to Ironwood migration window this is naturally dense, which is the whole reason to batch the mass, non-time-sensitive migration event and not time-sensitive commerce. Outside that window, or in a globally thin period, batches can be small or singular.

Two honest points follow. First, the flush cadence is capped by transaction expiry (the hub must flush before the tightest queued expiry, in practice well under 20 blocks), so the window **cannot** be widened to wait for more migrations to accumulate. There is no lever to trade latency for a bigger batch past that ceiling. Second, the only backstop for a thin window is hub-generated decoy migrations, and those cost real on-chain value, so they are a last resort, not the primary mechanism. The batch-timing anonymity is a genuine *additional* protection when density is there, layered on top of the robust IP-unlinking that Nym provides regardless of volume. Do not present the batch-timing property as if it held at any volume; report the achieved batch size.

## Broadcast is delayed, and the shim accepts before the chain does

The shim returns an accepted response to the wallet immediately, synthesizing a success as soon as it has queued the migration for the hub. But the transaction is not in any mempool until the hub flushes, which can be up to roughly 25 minutes later (blocks target about 75 seconds, and the flush runs on a strict block cadence under 20 blocks). Until then, a wallet that polls "is my transaction in the mempool or confirmed?" is asking the operator's backing lwd, which passes the query through and has no knowledge of the queued migration, so it will answer "not found" for minutes.

Migrations are not time-sensitive, so the delay itself is acceptable by design (this is exactly why the migration case is the one batched near-term). The real cost is UX: the pending gap can confuse a wallet UI or trigger a resend. The system tolerates resends (the hub dedups by txid, and the shim is idempotent per txid within a window), but the pending-state experience must be defined rather than left to accident: either wallets accept a bounded pending window for migrations, or the shim answers pending-status for txids it has queued. A related sharp edge: because the shim returns success before the hub validates and broadcasts, an invalid migration receives a false success and fails silently at flush. The mitigation is stateless pre-validation (parseable, not already expired) at the shim and again at the hub; full consensus validity is only known at broadcast, and surfacing a late hub-side failure to the client is out of near-term scope.

## Retain-until-confirmed is a hard requirement, because the hub is diskless

The hub runs in an attested enclave with no disk. Its pending queue and its awaiting-confirmation set live in RAM. A hub crash loses them. That single fact forces a non-negotiable obligation onto the shim: **the shim must retain each migration until it observes the transaction confirmed on-chain, not merely until it gets an Ack from a hub, and re-submit if a hub crash lost it.** Without shim-side retain-until-confirmed, a hub crash between accept and publish would silently drop a migration that the wallet already believes was accepted.

This is why the design pushes durability to the shim rather than giving the hub a disk. A diskless hub keeps the enclave's trusted computing base small and its restarts cheap, at the price of making the shim the durable party. The shim uses each migration's expiry slack (roughly 25 minutes to 2 hours depending on the wallet family) as its retry budget: it holds, retries, and fails over across hubs, and only gives up into the last-resort direct broadcast (below) if expiry approaches. The shim's own restart durability is weaker (it too is diskless, so an in-flight migration in RAM is lost on a shim restart); the mitigation there is to keep the Ack-pending window short and rely on the wallet's resend plus hub dedup. The engineering of the queue, dedup, and confirmation tracking lives with [the hub](./hub.md); the point for this chapter is that diskless-hub plus retain-until-confirmed-shim is a coupled pair, and neither half is optional.

## The trust root is AWS and the hardware, not math

The operator-blindness and hub-blindness guarantees are real and verifiable, but they rest on a hardware root of trust, not on cryptography that stands alone. A wallet (or a wallet developer acting as trust proxy) checks the shim's and hub's attestations against the AWS Nitro root, confirms the reproducible-build hash matches, and thereby knows the attested software is what is running and that keys were born inside the enclaves. That chain is only as strong as the AWS Nitro platform and the physical boundary of the hardware. If you do not trust AWS and the hardware, the near-term system does not give you a purely mathematical fallback. The mechanics of attestation, the reproducible StageX build, STEVE, and the keymaker quorum are covered in [trust](./trust.md); the honest-limits point is simply that they terminate at a hardware manufacturer and a cloud provider, not at a proof.

This is the specific gap that the deferred PIR layer (V3) is meant to close. PIR makes query privacy hold *via math*, hardware-independent, and closes the access-pattern and IO-pattern leaks a Nitro enclave structurally has when its state is parent-mediated at mainnet scale. TEE and PIR are complementary, not equivalent: they have distinct failure modes (a TEE fails on hardware-manufacturer or physical-boundary compromise; PIR fails on cryptographic or software flaws), so the endgame uses both, defense in depth, with PIR as the trust-root-removal step. Near-term, the trust root is AWS plus the hardware, and that is stated as a limit, not hidden. The path that removes it is in the [roadmap](./roadmap.md).

## Hub resilience, and the concentration of trust

The hub must hold every migration in order to publish it, which makes a single hub both a liveness risk (an outage would stall migrations) and a concentration of trust (all cross-operator batching converges on it, run by Caution at launch). The design answers the liveness risk directly and bounds the trust concentration, but it does not eliminate the fact that the hub is a central point in the near-term system.

The resilience measures, stated as honest limits and detailed as engineering in [the hub](./hub.md):

- **At least two attested hubs with shim failover.** A shim prefers a primary hub (so batches converge there and stay dense) and fails over to a hot standby only when the primary is unreachable. An outage on one hub does not stop migrations.
- **A single shared hub key across all instances**, provisioned to each attested hub by the keymaker quorum. This is what makes failover clean: a shim encrypts to "the hub key," and any instance can decrypt, dedup, and publish. Per-hub keys would force re-encryption on failover and could strand a migration whose hub died mid-flight.
- **Dedup by txid at every hub.** If failover causes a migration to reach two hubs, both may publish; the second on-chain submission is a harmless already-known duplicate. No cross-hub state sync is needed near-term: harmless duplicates are accepted over the complexity of a shared published-set.
- **Shim hold-and-retry using expiry slack.** The shim rides out transient blips with each migration's expiry margin before escalating.
- **Last-resort direct broadcast over Nym.** If every hub is unreachable and a queued migration nears expiry, the shim broadcasts it directly over Nym rather than let it expire. The IP is still hidden (Nym), but the batching is lost for that one transaction, so its timing anonymity degrades even as it still confirms.

The governing principle: an outage degrades privacy at the margin (a lost batch, a direct broadcast), never liveness (a migration never simply expires in a buffer). Because the hubs are attested enclaves, no hub operator sees cleartext, and the multi-org consortium governs the keys long-term (see [trust](./trust.md)); at launch, a single trusted entity stands up the hub, with the consortium to follow. That launch concentration is itself part of the honest accounting: the trust distribution is a goal, not a shipped property on day one.

## How to report these limits

When describing the system publicly, lead with the robust, volume-independent claim (IP unlinking for the migration broadcast, via Nym and the TEE) and qualify the conditional ones: the batch-timing anonymity depends on migration density and can be size one; the operator can infer the fact of a migration though not its amount; the broadcast is delayed; the trust root is AWS and the hardware, not math. Report the achieved batch size rather than an assumed one. Underclaiming here is cheap, and overclaiming is the failure mode this chapter exists to prevent.
